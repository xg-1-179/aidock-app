# 连接策略：中转只能是备选，不能是前提

> 这一条是本项目的**第一设计原则**。原插件折腾一整天没连上的根本原因就在这，不是加密、不是二维码，是连接拓扑被写死了。

## 一、原插件为什么"非要走中转"

实测到的四层原因，逐条都有证据：

1. **App 强制要求二维码里带 `relayUrl`**
   去掉中转后手机端点「扫码」，App 直接判「这台电脑只给了局域网地址，手机现在不在同一个网络里」，
   连试都不试。这句话是 App 内置文案，插件里 grep 不到。
2. **带了中转又优先撞中转**
   中转 `https://ai-hub-de-1.wnluo.com/api/mobile/v1/mux` 的 WebSocket 入口被前置 nginx（腾讯 EdgeOne）
   回 **503**，App 仍先走它，撞满超时才回落到直连 → 单次连接 20 多秒、切两次通道。
3. **公网 IP 塞进 `lanUrls` 不被认**
   App 把 `lanUrls` 一律当"内网"处理，公网地址放进去等于没放。
4. **插件把私网候选永远排第一**
   `lib/relay/lan-network.cjs` 的 `advertisedCandidates()` 只要网卡上有私网就不看公网；
   `withManualCandidate()` 又把手填地址追加在末尾。于是二维码里第一位永远是 `10.2.0.12:41873`
   —— 那是腾讯云内网，手机永远拨不到。

结论：**拓扑写死在代码里，客户端和插件都不肯先试能通的那条**。

## 二、我们的规则

| 原则 | 具体做法 |
|---|---|
| 不依赖中转 | 直连（公网 IP / 局域网 / Tailcat 隧道 / P2P）任一可用即可完成配对与通信 |
| 中转是"其一"不是"前提" | 二维码里每个通道都是平等的候选，没有"必须存在"的字段 |
| 多路并行探测，先到先用 | 客户端对全部候选**同时**发起 TCP/TLS 握手，单个通道超时 3 秒，第一个成功就采用 |
| 路径记忆 | 成功后记住这条路径并优先复用；连续失败 2 次才重新全量探测 |
| 可自建中转 | 公共中转只做默认值，进阶用户填自己的 relay（一行地址） |
| 连接诊断可见 | App 内一页显示每个候选的探测结果（延迟/失败原因），用户自己能看出卡在哪 |
| 配对码与扫码等价 | 六位码走同一套 v2 握手，扫码只是把候选列表塞进二维码 |

## 三、落地要点

- 插件的二维码 payload：`candidates: [{scheme:'http'|'https'|'tailcat'|'p2p', host, port, ...}]`，
  **有序但不等权**，客户端必须全部并行试，不得按顺序超时等待。
- 客户端把"上次成功的通道指纹"落盘，冷启动先试它（3 秒），失败立刻转并行全探测。
- 服务端不做"公网/内网"判断，只如实上报所有可达地址（含手动配置的公网地址、IPv6）。
- 中转不可用时前端要显示"中转不可用，已使用直连"，而不是静默等待。
